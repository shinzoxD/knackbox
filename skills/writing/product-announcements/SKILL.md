# Product Announcements

Announcements sell outcomes, not ticket IDs. Be accurate: do not claim what
the product cannot do today.

## Workflow

1. Audience (users, admins, internal, press-lite) and channel (email, blog, in-app).
2. Core value prop in one sentence; 1–3 supporting benefits.
3. Who gets it (plan tiers, regions, flags) and when.
4. How to start (CTA) and where to learn more.
5. Proof (customers, metrics) only if provided.
6. Risks/caveats (beta, breaking changes) honestly.

## Output format

```markdown
# <Headline>

**Subhead:** …

## Why it matters
…

## What's new
- benefit-led bullets

## Get started
CTA + steps

## Details / availability
…

## FAQ (optional)
…
```

## Rules

1. No invented metrics, logos, or launch dates.
2. Benefit → feature, not feature dump.
3. Match channel length (in-app shorter than blog).
4. Breaking changes get plain-language migration notes.
5. Separate internal stakeholder note if both audiences needed.
6. Avoid hype words without substance ("revolutionary", "seamless") unless user brand voice requires — still ground in facts.

## Edge cases

- **Quiet launch / beta:** set expectations; invite feedback.
- **Multiple features:** theme them; don't laundry-list 20 equal bullets.
- **Regulated claims:** stay conservative; mark legal review needed.
